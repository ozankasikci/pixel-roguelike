<objective>
Replace the level editor's tight busy-loop (`glfwPollEvents` + render every frame) with a hybrid poll/wait strategy that uses `glfwWaitEventsTimeout()` when idle and `glfwPollEvents()` when continuous rendering is needed.

Purpose: The editor currently burns near-100% CPU even when completely idle because `glfwPollEvents()` returns immediately and the loop busy-spins. macOS vsync via OpenGL 4.1 is unreliable (documented GLFW issues on M1/Monterey/Mojave). Industry-standard fix per the ImGui wiki is `glfwWaitEventsTimeout()` gated by activity detection.

Output: Modified `apps/level_editor/main.cpp` with idle throttling — near-zero CPU when idle, full-speed when interacting.
</objective>

    2. Replace the main loop (lines 2075-2078) from:
       ```cpp
       while (!window.shouldClose()) {
           window.pollEvents();
           renderFrame();
       }
       ```
       To:
       ```cpp
       while (!window.shouldClose()) {
           const bool needsContinuousRendering = cameraAnim.active
               || (ui.playPreview && runtimePreviewSession.captured())
               || ImGui::GetIO().WantCaptureMouse
               || ImGui::GetIO().WantCaptureKeyboard;

           if (needsContinuousRendering) {
               glfwPollEvents();
           } else if (glfwGetWindowAttrib(window.handle(), GLFW_FOCUSED) == 0) {
               glfwWaitEventsTimeout(kUnfocusedTimeoutSeconds);
           } else {
               glfwWaitEventsTimeout(kIdleTimeoutSeconds);
           }

           renderFrame();
       }
       ```

    IMPORTANT constraints:
    - Call `glfwWaitEventsTimeout` / `glfwPollEvents` directly (not through Window wrapper) since main.cpp already includes `<GLFW/glfw3.h>` and the conditional logic belongs in the editor, not the engine.
    - Use exactly ONE event function per loop iteration (never both — per GLFW docs, calling both processes events twice causing erratic timing).
    - Do NOT touch the `renderStartupProgress` function at line 198 — that `pollEvents` call is for the startup loading screen, not the main loop.
    - Do NOT modify `Window.h` or `Window.cpp` — the throttling policy is editor-specific, not engine-level.

    Why these specific flags:
    - `cameraAnim.active`: F-key focus animation must run at full speed for smooth interpolation
    - `ui.playPreview && runtimePreviewSession.captured()`: runtime game preview needs full framerate
    - `WantCaptureMouse`: covers hovering over ImGui panels, dragging sliders, gizmo interaction
    - `WantCaptureKeyboard`: covers text input in inspector fields
    - When none are true, user is idle or just looking at the viewport with nothing animating — safe to throttle
